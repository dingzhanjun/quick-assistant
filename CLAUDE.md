# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Multi-tenant SaaS for restaurants: customers phone the restaurant, a LiveKit voice agent takes the order, and staff manage menus/orders/settings in a web dashboard. A platform admin manages tenants. Early-stage: auth, DB schema and the agent API exist; the dashboard UI is mostly a placeholder.

## Layout

- `apps/web` — Next.js (App Router, TS, Tailwind, pnpm workspace member). Dashboard + the internal API the agent calls. Next.js here is a newer version than most training data: read `apps/web/AGENTS.md` and `node_modules/next/dist/docs/` before writing Next code.
- `apps/agent` — Python LiveKit Agents worker, managed with `uv` (not pip). Package at `src/order_agent`.
- Root `package.json` / `pnpm-workspace.yaml` only cover `apps/web`; the agent is outside the pnpm workspace.

Docs: `docs/ARCHITECTURE.md` (components, call/print flows, data, security, CI/CD) and `docs/SYSTEM_SETUP.md` (every account, the server, GitHub, phone line, AI keys, first restaurant, Raspberry Pi printer, go-live checklist, troubleshooting). Keep them in step when the system changes.

## Commands

Run from repo root unless noted. Copy `.env.example` to `.env` first.

- `pnpm install` — JS deps; `cd apps/agent && uv sync` — Python deps
- `pnpm db:up` — start local Postgres (docker compose)
- `pnpm --filter web db:seed` — idempotent demo restaurant ("Demo Pizza", number `+14155550100`, 5 items); add `DEMO_OWNER_EMAIL=<signed-up email>` to also make that user its owner
- `pnpm dev:web` — Next dev server on :3000
- `pnpm dev:agent` — agent worker in dev mode (needs LiveKit + provider keys). For a local voice test without SIP: `cd apps/agent && uv run python -m order_agent.main console` (uses `DEV_CALLED_NUMBER` as the dialed number)
- `pnpm lint` — ESLint for web
- `pnpm --filter web db:generate` / `db:migrate` / `db:studio` — Drizzle migrations (SQL lands in `apps/web/drizzle/`; `db:migrate` needs the DB running)
- `pnpm --filter web build` — also the way to type-check: `tsc --noEmit` fails on `LayoutProps` until Next has generated its types

Tests (all run in CI): web unit + isolation + integration tests `pnpm --filter web test` (node:test against a migrated Postgres; the script runs every file in parallel EXCEPT `tests/jobs*.test.ts`, which share the global job queue and run afterwards one at a time; test files must only delete their OWN rows, never e.g. all `sms` jobs; the sign-in rate-limit tests make a second full run inside a minute fail, needs `DATABASE_URL`, `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL`, `GOOGLE_CLIENT_ID/SECRET`); browser tests `pnpm --filter web build && pnpm --filter web test:e2e` (Playwright); agent tests `cd apps/agent && uv run python -m pytest -q`; AI evals `cd apps/agent && uv run python -m evals.run_evals` (paid LLM calls, never xAI by default).

## Architecture

Call flow: SIP trunk -> LiveKit room -> agent worker joins. In `main.py:entrypoint` the agent reads the dialed number from the participant's SIP attributes (`sip.trunkPhoneNumber`) and uses it to resolve the **tenant**, then loads that tenant's menu into the LLM prompt. STT (Deepgram) -> LLM (OpenAI/DeepSeek, admin-selectable) -> TTS (Deepgram Aura), with Silero VAD.

Key boundary: **the agent never touches the database.** It calls the web app's `/api/agent/*` routes (`apps/agent/src/order_agent/api.py`), authenticated with the shared `AGENT_API_KEY` bearer token. All tenant resolution, validation and persistence belong in those Next route handlers (`apps/web/src/app/api/agent/{menu,orders}/route.ts`), so tenant isolation is enforced in one place.

Tenancy: a tenant is a Better Auth **organization** (one per restaurant). Every app table in `src/db/schema.ts` carries `tenant_id` -> `organization.id`; `phone_numbers` maps dialed E.164 number -> tenant and is the entry point for calls; each restaurant has exactly ONE agent number (unique index on `tenant_id`; `addTenantNumber` refuses a second, remove first; the seed only adds the demo number when the demo restaurant has none). Always scope queries by tenant. Order prices/names are looked up server-side from `menu_items` (never trusted from the agent) and snapshotted into `order_items`; `order_number` is allocated per tenant under an advisory lock.

Auth: Better Auth (`src/lib/auth.ts`, mounted at `/api/auth/[...all]`) with Google OAuth and email+password (verification required; links go through `src/lib/email.ts` — Resend if `RESEND_API_KEY` is set, otherwise printed to the web server console, also used for password reset at `/forgot-password` → `/reset-password`). Admin emails (`PLATFORM_ADMIN_EMAILS`) can only be created via verified Google sign-in — password sign-up for them is rejected, and `requirePlatformAdmin()` also requires `emailVerified`. Brand-new system without Google set up: `PLATFORM_ADMIN_PASSWORD` (>= 12 chars) + `PLATFORM_ADMIN_EMAILS` makes `ensureBootstrapAdmin()` (`lib/bootstrap-admin.ts`, called from `instrumentation.ts` at startup, advisory-locked so replicas do not race) create the FIRST listed email as a verified `admin` with a credential account, only when NO admin exists yet and never touching an existing account with that email (audit `admin.bootstrapped`); `authPolicy.adminPasswordLoginAllowed()` lets listed admin emails use password sign-in ONLY while that variable is set, so deleting it returns to Google-only admins (the stored hash stays but cannot be used). Tests: `tests/bootstrap-admin.test.ts`. `requireTenant()` trusts the session's active organization only while the user is still a member, and otherwise falls back to their first membership (fresh sessions have no active organization). The dashboard nav has a restaurant switcher (`app/dashboard/switcher.tsx` + `components/restaurant-switcher.tsx`) that calls `organization.setActive`. Auth uses `organization` and `admin` plugins, Drizzle adapter. Platform admin = user with `admin` role. `src/db/auth-schema.ts` is generated by `pnpm dlx @better-auth/cli generate --config src/lib/auth.ts --output src/db/auth-schema.ts`; regenerate it (then `db:generate`) after changing auth plugins, and don't hand-edit it.

Next config: `cacheComponents` is on, so reading `headers()`/session must happen inside a `<Suspense>` boundary (see `app/dashboard/page.tsx`). `next.config.ts` and `drizzle.config.ts` load the single root `.env`.

Settings (`app/dashboard/settings/`) is split into tabs, one route each so a tab only loads its own data: General (`page.tsx`: phone number, details, opening hours), Notifications (`notifications/`), Team (`team/`), Kitchen printing (`printing/`); `layout.tsx` + `tabs.tsx` render the tab bar, and settings actions call `revalidatePath("/dashboard/settings", "layout")` so every tab refreshes. A new settings section = a new tab route plus an entry in `tabs.tsx`.

UI: React Suite (`rsuite`, migration plan and decisions in `UI_MIGRATION_PLAN.md`) + Tailwind for layout. Pages use thin adapters in `src/components/ui` (`Button`, `Input`, `Textarea`, `Switch`, `Select`, `Card`, `Dialog`, `Label`, `Table`) plus `ConfirmButton`, `ThemeToggle` and `lib/toast.tsx` (toasts); they keep the old shadcn-style props and render rsuite components, so use them (or import `rsuite/<Component>` directly for anything richer, e.g. `rsuite/DatePicker`). NEVER a native `<select>` (use `ui/select`). Font: Roboto (`next/font` in `app/layout.tsx`, stack in `--app-font` in `globals.css`, shared with rsuite through `--rs-font-family-base`). Light/dark/system theme: `components/providers.tsx` (next-themes + rsuite `CustomProvider`). CSS layer order in `globals.css` (`theme, base, rsuite, components, utilities`) is load-bearing: rsuite above Tailwind's preflight, below utilities. Helpers that server components call must not live in a `"use client"` file (see `ui/button-variants.ts`). `rsuite` Toggle ignores `aria-label`: give `Switch` a `label`. e2e: click switches and checkboxes with `{ force: true }`; pickers via `pick(page, label, option)` in `e2e/helpers.ts`. Text colours must be the theme-aware tokens (`text-muted-foreground`, `text-destructive-text`, `text-success-text`, `text-warning-text`, `text-primary-text`), never fixed Tailwind greys / reds (unreadable in dark mode). Button colours are overridden in `globals.css` for AA contrast. QA scans: `A11Y=1 pnpm test:e2e e2e/a11y.spec.ts` (axe, light + dark, console errors) and `VISUAL_LABEL=name [VISUAL_SCHEME=dark] pnpm test:e2e e2e/visual.spec.ts` (screenshots). A streamed page briefly holds a hidden duplicate of its content, so strict `getByText` right after `goto` needs `.first()` / `exact`. Dashboard pages live under `app/dashboard/` and use `requireTenant()` (`src/lib/tenant.ts`) to get the active restaurant; mutations are server actions that must scope every query by `tenantId` (see `dashboard/menu/actions.ts`).

LLM choice: the platform admin picks provider/model in `/admin` (stored in the single-row `platform_settings` table; allow-list of providers in `src/lib/llm-providers.ts`, kept DB-free so client components can import it). The agent fetches it per call from `/api/agent/config` (`build_llm()` in `main.py`, falls back to OpenAI `gpt-4o-mini` if unreachable). API keys are never stored in the DB — they come from the agent's env (`OPENAI_API_KEY`, `DEEPSEEK_API_KEY`). To add a provider, extend `LLM_PROVIDERS`, the `llm_provider` enum in `schema.ts` (+ migration) and `build_llm()`.

New-order emails: `POST /api/agent/orders` calls `notifyNewOrder()` (`src/lib/notify.ts`) via `after()` so email never delays or fails the order. Recipients = `tenant_settings.notify_emails` (set in `/dashboard/settings`), else the tenant's `owner` members; `notify_new_orders` turns it off. `tenant_settings` mixes platform-controlled (`suspended`) and restaurant-controlled (`notify_*`) columns, so upserts must only touch their own columns.

Route protection: `src/proxy.ts` (Next 16's renamed middleware) only does a cheap session-cookie check and 307s signed-out visitors from `/dashboard`, `/admin`, `/onboarding`; real authorization stays in `requireTenant()` / `requirePlatformAdmin()` (with `cacheComponents`, in-page `redirect()`/`notFound()` can't change the 200 status).

Platform admin: `/admin` (guarded by `requirePlatformAdmin()` in `src/lib/admin.ts`, 404 for non-admins) lists tenants and can suspend them via `tenant_settings.suspended`. Admins are users with `role = 'admin'` or an email in `PLATFORM_ADMIN_EMAILS` (the latter also assigns the role at first sign-in). Suspended tenants get 403 from `/api/agent/*`; the agent apologizes and hangs up. Suspension does not yet block the tenant's own dashboard.

Docker Compose (one file): `docker-compose.yml` is the whole production stack and is all a server needs next to a `.env` (copied from `.env.prod.example`): `docker compose up -d` pulls the images, `migrate` runs before web, everything starts. The Caddyfile and the backup / retention scripts are INLINE as top-level `configs:` with `content:` (`$` written `$$`; `docker compose config` prints them re-escaped, so verify by reading the file inside a container). Each app service also has a `build:` block, so a clone can `docker compose build`; its image is `${IMAGE_PREFIX:-ghcr.io/dingzhanjun/quick-assistant}/{web,migrate,agent}:${IMAGE_TAG:-latest}`, exactly what CI pushes to GHCR on main. GHCR packages are created PRIVATE by CI: make web/migrate/agent public once so restaurants need no login. CI builds amd64 only; `docker-compose.publish.yml` adds `platforms: [linux/amd64, linux/arm64]` for a manual multi-arch `docker compose -f docker-compose.yml -f docker-compose.publish.yml build --push` (needs `docker buildx create --use` and a `write:packages` token). The GitHub repo must be named `quick-assistant` for CI's image path to match the default prefix. Needs Compose >= 2.23.1 (inline configs). `scripts/deploy.sh` (CI deploy, rollback by sha) uses the same file and `.env`. Verified: images build, inline files are byte-identical inside the containers, Caddy validates its config, the inline backup script writes a verified dump, db + migrate + web + worker come up healthy.

Deployment: single Ubuntu server with Docker Compose, see `docs/DEPLOY.md`. Images are built ONCE in CI (the `build-image` matrix job in `.github/workflows/ci.yml`, one job per image, GHA layer cache, official docker/* actions) and pushed to GHCR as `$IMAGE_PREFIX/{web,migrate,agent}:<full commit sha>` plus `:latest` (`IMAGE_PREFIX` = `ghcr.io/<owner>/<repo>`); the server only pulls. `docker-compose.yml` names an `image:` per service (and has `build:` blocks for developers); the server never builds, so to run the stack you need images CI already pushed. It runs web + db + one-shot `migrate` + `backup` + agent, plus ONE public entry chosen by `COMPOSE_PROFILES` in `.env`: `caddy` (HTTPS on 80/443, blocks `/api/agent/*` publicly in the inline Caddyfile) or `tunnel` (`cloudflared`, outbound only; the `/api/agent` block must be a Cloudflare WAF rule). The CI / rollback path is `scripts/deploy.sh <sha|latest|dev>` (a plain install just uses `docker compose up -d`) (backup -> pull -> migrate separately -> replace containers -> wait for health; the server has NO repo access: it only holds the deployment files copied by hand, listed in `docs/DEPLOY.md` "Deployment files", and must be updated when a commit changes them; pull/migrate failures leave the running site untouched; the sha is regex-validated since CI passes it over SSH to a forced command); rollback = deploy an older sha. The CI `deploy` job needs the `production` environment secrets in `docs/DEPLOY.md` (branches: `main` deploys GitHub environment `Prod`, `dev` deploys environment `Dev`, each with its own secrets/vars and server; `dev` images are tagged `dev`, `latest` is main only; via `appleboy/ssh-action`: `DEPLOY_PASSWORD` or `DEPLOY_SSH_KEY`, `DEPLOY_FINGERPRINT` for host-key pinning; a ForceCommand-restricted `deploy` user is recommended; with no secrets the job skips itself), and GitHub runners must reach the server over SSH (not for a server behind NAT). The `backup` compose service (inline `backup_sh` config) dumps daily, verifies the dump, and rotates; `scripts/backup-db.sh` triggers one on demand. Config is env-only via `.env`; images are built with dummy secrets and get real ones at runtime. `GET /api/health` pings the DB. The web build deliberately fails without `BETTER_AUTH_SECRET`; the DB client uses `prepare: false` so it also works behind transaction-mode poolers.

Language: calls are English only. A call starts with a scripted greeting in `OrderAgent.on_enter` (`greeting()`: "Thanks for calling X. This is an automated ordering assistant. What would you like to order?"), then the agent takes the order with the session's Deepgram STT/TTS. Scaling pieces for several web replicas: (1) login/sign-up rate limits are stored in the database (`rate_limit` table, Better Auth `rateLimit.storage: "database"`), not in process memory. (2) `lib/menu-cache.ts` keeps each restaurant's agent menu for `MENU_CACHE_SECONDS` (default 10, 0 = off) per process and shares one query across a burst of calls; menu/modifier actions call `invalidateMenu(tenantId)`; the order route always validates against the database, so a stale cached menu can never sell a sold-out dish. (3) Background jobs (`jobs` table, `lib/jobs.ts`): emails (new order, cancel/change, verification, reset, invitation) are QUEUED with `enqueueEmail()` and sent by a worker with retries (30 s, 2 min, 10 min, 30 min, 2 h; then `failed` + audit `system.job_failed`); claimed with `FOR UPDATE SKIP LOCKED` so any number of replicas can run it (`src/instrumentation.ts` starts a loop (`JOB_TICK_SECONDS`, default 5) that drains every due job in batches in each process where `jobWorkerEnabled()`, i.e. unless `JOB_WORKER=off`; local development and a single server therefore need nothing else. PRODUCTION runs a dedicated `worker` compose service and sets `JOB_WORKER=off` on `web`. The worker is its OWN small program, `apps/web/src/worker/main.ts`: only the job loop plus a stdlib health endpoint (`GET /health` on `WORKER_HEALTH_PORT`, default 3000: 200, or 503 when the DB is down or a due job waited more than `WORKER_LAG_SECONDS`), no Next.js, no auth library (it gets no auth secret or agent key). It is bundled with esbuild (`pnpm --filter web build:worker` -> `dist/worker.cjs`, ~330 KB, run by the Dockerfile `build` stage) and copied into the SAME web image as `apps/web/worker.cjs`; the compose service just overrides the command (`node apps/web/worker.cjs`, `JOB_TICK_SECONDS` 2, 128 MB limit (about 15 MB measured idle in the real image), nothing published); locally `pnpm --filter web worker` runs it from source, so sending never competes with requests; `kickJobs()` does nothing in a process with the worker off. `GET /api/health/worker` returns 503 when a due job has waited more than `WORKER_LAG_SECONDS` (default 120): it is the worker container's health check, `deploy.sh` warns if the worker is not healthy, and external monitors can use it. Platform admins browse the queue at `/admin/jobs` ("Email & text queue": worker health line, counts, filters by status and type, failed jobs with their error, **Retry**, **Retry all failed** (max 200), **Delete**; `retryJob`/`retryFailedJobs`/`deleteJob` in `admin/jobs/actions.ts`, audited as `admin.job_retried` / `admin.job_deleted`, phone numbers masked). Tests: `tests/jobs-admin.test.ts`, `tests/jobs-worker.test.ts` (builds the bundle and runs it as a real process), `e2e/zz-admin-audit.spec.ts`); the same loop sends ONE "order not acknowledged" reminder email + audit `order.unacknowledged` for orders still `new` after `UNACK_ALERT_MINUTES` (default 5, `orders.unack_alerted_at`) and purges old counters/jobs. (4) Row-level security (migration 0016/0017): `withTenant(tenantId, (tx) => ...)` in `lib/tenant-db.ts` runs as the low-privilege role `order_app` with `app.tenant_id` set, so the DATABASE only shows/accepts that restaurant's rows (missing tenant filter = no rows, fail closed); `order_app` cannot read `audit_logs`/`jobs`, cannot change `suspended` or phone numbers (column grants), and is used by all dashboard actions and pages and the agent menu/orders/lookup/cancel routes. Platform code (admin pages, jobs, audit, number lookup, calls rate limits) keeps using `db`. **New tables that hold restaurant data need: `tenant_id` (or a parent), `ENABLE ROW LEVEL SECURITY`, a `tenant_isolation` policy and GRANTs to `order_app`; `tests/rls.test.ts` fails if a table with a `tenant_id` column lacks RLS.** Pass `tx` (not `db`) to helpers inside `withTenant`.

Worker capacity: `worker_options()` in `main.py` reads `AGENT_*` env settings (`AGENT_MAX_CALLS` hard cap per container via `make_load_fnc`: load = max(CPU, 0.6 x calls/max), 1.0 at the cap; idle processes, memory warn/limit, `AGENT_DRAIN_SECONDS` default 900 with compose `stop_grace_period` 16m so deploys do not kill calls, Prometheus port) and compose has `AGENT_REPLICAS`; see `docs/DEPLOY.md` "Scaling the voice agent". Live orders board: migration 0013 adds a trigger on `orders` that runs `pg_notify('orders_changed', tenant_id)`; `lib/order-events.ts` keeps one LISTEN connection per web process (`DATABASE_LISTEN_URL` for pooled setups) and fans out per restaurant to `/api/dashboard/orders/stream` (SSE: `ready`, `orders`, 20 s heartbeat, 30 min lifetime); `orders-board.tsx` listens with `EventSource`, refreshes on events (debounced), shows a Live/Reconnecting badge, and polls only as a safety net (60 s live, 5 s when disconnected); `resolveTenant()` returns `{ok:false, redirect}` for routes that cannot redirect. Tests: `tests/orders-live.test.ts`, `tests/test_worker_options.py`, e2e live-board test. Pickup time: every order has one. When the caller is done choosing items the agent asks "as soon as possible, or a little later?", asks for the exact time if they only say "later", then says the filler and calls `set_pickup_time("asap" | "HH:MM" 24-hour)` BEFORE the read-back; `submit_order` is refused in code until one is saved and the time is part of the idempotency key. The web side (`/api/agent/orders`, `pickup: {type: asap} | {type: time, time}`) is authoritative: a time is today in the restaurant's time zone (`tenant_settings.timezone`), refused if already past (2 min slack, `pickup_in_past`) or outside the opening hours (`pickup_closed`, with the hours); stored as `orders.pickup_at` (null = ASAP), shown on the orders board and in the new-order email, returned by `/api/agent/orders/lookup` so a changed order keeps it, and logged in the audit details (`src/lib/pickup.ts`). Evals `*-pickup-*`. Each time the caller confirms an item the agent first says ONE short filler ("Sure." or "OK.", varied) and calls `add_item` in the same turn, then continues WITHOUT repeating Sure/OK; an extra charge is announced alone ("Large adds two dollars."). Notes passed to `add_item` are written in English, as the kitchen reads English.

Experimental Grok mode: `VOICE_MODE=grok` (+ `XAI_API_KEY`, optional `GROK_VOICE`/`GROK_MODEL`) makes `entrypoint()` use `xai.realtime.RealtimeModel` (speech-to-speech) instead of Deepgram STT + admin-selected LLM + TTS. The realtime model cannot read a script aloud, so `OrderAgent(opening=...)` instructs it to say the greeting; tools, code-computed totals and English notes are the same. Untested with real audio (no key yet).

Modifiers (menu options): `modifier_groups` (per tenant: name, `required`, `maxSelect`) hold `modifier_options` (name, `price_delta_cents`, `available`) and attach to menu items through `menu_item_modifier_groups` (groups are reusable across dishes). Managed at `/dashboard/modifiers` and attached per dish in the menu editor. `/api/agent/menu` returns each item with its `modifierGroups`; `/api/agent/orders` accepts `option_ids` per line and VALIDATES them server-side with `resolveSelection()` in `src/lib/modifiers.ts` (option must belong to a group attached to that exact item and tenant, required groups answered, `maxSelect` respected), then snapshots them into `order_items.modifiers` jsonb (group, option, price delta) so later menu edits don't rewrite past orders. Line price = base + sum of deltas; `lineUnitCents()` lives in client-safe `src/lib/pricing.ts`. In the agent, options are referred to by short codes (`o1`, `o2`, ...) from `option_codes()`; `add_item(item_id, quantity, options=[codes], notes)` re-checks the choices in code (missing required choice => refused with a message telling the model to ask), merges identical lines, and its result spells out the surcharge so the prompt can make the agent say only "Large adds two dollars." (the running total is NOT repeated mid-order: add/remove results omit it, and only `get_order` at the final read-back states it; all totals computed in code).

Categories: `categories` (per tenant: `name`, `sort_order`, unique name ignoring case, enforced in `saveCategory`) and the many-to-many `menu_item_categories` (a dish can be in several; RLS through its dish, and the category must be the same tenant's). Owners manage them at `/dashboard/categories` (add/edit/delete, up/down order buttons) and tick them per dish in the menu editor (rsuite `CheckPicker`, no native select); deleting a category keeps the dishes. The Menu tab lists dishes under one heading per category (a multi-category dish appears under each, the rest under "Other") with a category filter. `/api/agent/menu` returns `categories: [{name, position}]` per item (`categoriesForItems()` in `src/lib/categories.ts`, `position` = owner's order). Agent: big-menu overview is grouped by category (`_overview()`), full-menu lines carry `| category: ...`, and `search_menu` answers a category name ("drinks") by listing that category's dishes (`MenuIndex.match_category`, only when no dish is named exactly that). Every category action is audited (`category.*`) and in `tests/tenant-isolation.test.ts`; `tests/categories.test.ts`, `e2e/owner.spec.ts`, `tests/test_menu_search.py`, `tests/test_order_agent.py`. Not done: categories on the kitchen ticket, hiding a category from the agent (time-of-day menus). `rsuite` Modal ignores Esc while a picker popup is open (`ui/dialog.tsx`), so Esc closes only the picker.

Copy menu from another restaurant (Menu tab, owner only, shown only when the user OWNS at least one other restaurant; for chains with several locations, each location being its own restaurant with its own number): `previewMenuCopy(sourceId, mode)` / `applyMenuCopy(sourceId, mode)` in `dashboard/menu/copy-actions.ts`, logic in `lib/menu-copy.ts` (`readMenuSnapshot` reads a whole menu with every link written by NAME, `planMenuCopy` is the dry run). The source must be a restaurant where the current user has the `owner` role (checked against `member`; the menu is read through `withTenant(sourceId)` only after that check), never the current one. Copies dishes, categories (in order), modifier groups with their options, and the dish-category / dish-modifier links, in ONE transaction under an advisory lock; matched by name ignoring case; nothing is ever deleted and links are only added. Mode `add` (default) leaves everything that already exists untouched; `update` also brings existing dishes (price, description, availability) and existing groups/options in line. Dishes whose name is ambiguous in the destination are skipped and reported. Audited as one `menu.copied` entry. Tests: `tests/menu-copy.test.ts`, `tests/tenant-isolation.test.ts`, `e2e/copy-menu.spec.ts`. Not built: a linked menu shared by several locations (see the multi-location discussion: a later "group" feature), and one shared phone number for several locations (would need a location question in the call).

Menu CSV import/export (Menu tab, owner only): `lib/menu-csv.ts` (client-safe: RFC 4180 parser, header aliases, per-row validation, `menuToCsv` with a BOM so Excel reads accented names, `TEMPLATE_CSV`; limits 1000 rows / ~500 KB) and `lib/menu-import.ts` (`planMenuImport`: matches dishes by name ignoring case, compares only the columns present in the file, finds categories to create). Columns: `name`, `price` (required), `description`, `available`, `categories` (split on `; | ,`). A column absent from the file leaves that field alone; a column present REPLACES it (an empty cell clears; an empty `categories` cell removes the dish's categories). Never deletes dishes, never touches modifiers, new categories are appended in file order. `previewMenuImport(csv)` is a dry run, `applyMenuImport(csv)` re-parses and applies in ONE transaction, and any file error (bad price, duplicate name, two existing dishes with the same name) refuses the whole file. Audited as one `menu.imported` entry (counts + names). Tests: `tests/menu-csv.test.ts`, `tests/menu-import.test.ts`, `tests/tenant-isolation.test.ts`, `e2e/owner.spec.ts`.

Texting the order (SMS): when `SMS_PROVIDER` is configured (`twilio` | `plivo` | `log` for dev, `lib/sms.ts`; empty = OFF) AND the restaurant's `tenant_settings.text_order_link` is on (Settings -> Notifications, default on), `/api/agent/menu` returns `text_orders: true` and the agent changes its ending: after `submit_order` it does NOT arm the hang-up; it says the order number and asks ONE question (text the order to the number they are calling from, or another number?). Decline -> "No problem. Thank you for calling, goodbye!" + `end_call`; yes -> tool `text_order()` (no number = caller id); another number -> `text_order("digits")`, the SYSTEM reads it back with `session.say` (`order_text.read_back`, digit by digit, the model never says digits; fallback: the model reads it back if speech output fails) and `confirm_text_number()` sends after a yes. `api.request_order_text` -> `POST /api/agent/orders/sms` only RECORDS the number (normalised by `parseTextNumber`, order must be placed within 30 min, not cancelled, at most 2 numbers per order, at most 3 order texts per destination number per day across ALL restaurants, `order.text_requested` audit with masked number): `orders.contact_number` + `sms_count`. The text itself is queued by `textOrderLink()` (`lib/order-sms.ts`, an `sms` job on the same worker/retries as email, failure -> `system.job_failed`, audit `order.text_sent`) when the RESTAURANT CONFIRMS the order (`setOrderStatus` leaving `new`: Confirm & Print / Start preparing), or at once if the order was already confirmed when the customer gave the number; claimed through `orders.sms_sent_at` so it goes out once (a corrected number clears it and may send once more); nothing is sent for cancelled orders, orders without a number, or when the restaurant switched texting off. The text is exactly "Thanks for your order, to view your order #N, tap this link: <BETTER_AUTH_URL>/orders/<token>". `orders.public_token` (22 chars, 128 random bits, set at order creation) is the only key of the public page `/orders/[token]` (no sign-in, no phone numbers, noindex, auto-refreshing status, expires after 30 days, unknown token = not-found page); the page also shows the restaurant's address (map link) and human line (`tel:` link) from `tenant_settings`; the orders board shows the customer's number ("they get the order link by text when you confirm" until sent) and a link to that page. Retention (``retention_sh` in docker-compose.yml`) clears `contact_number` with `caller_number`. Tests: `tests/order-sms.test.ts`, `tests/test_order_text.py`, `tests/test_text_order_flow.py`, evals `*-text-*`, e2e in `staff-and-orders.spec.ts`. Not verified with a real SMS provider or real audio; US delivery needs 10DLC / toll-free registration.

Change pickup time / cancellation texts: every ACTIVE order card (new, preparing, ready) has a "Change Pickup Time" button (`orders/change-pickup.tsx`, server action `changePickupTime(id, "HH:MM" | null)`, any member, today only, must still be ahead, opening hours not enforced). It stores `orders.new_pickup_at` ("new pickup time"; `pickup_at` keeps what the customer asked for, `null` = back to the original) and `effectivePickup()` (`lib/pickup.ts`) is the time that counts: board ("changed, was ..."), kitchen ticket (reprints), the customer's order page ("updated by the restaurant") and the phone agent's order lookup. Setting a time texts the customer "Your pickup time for order #N is now H:MM PM. Details: <link>" (`textPickupChange`, one text per distinct time; resetting texts nothing; audit `order.pickup_changed`). A CANCELLED order texts "Your order #N has been cancelled. Details: <link>" (`textOrderCancelled`, once) when the restaurant cancels on the board or the customer cancels by phone, NOT when a changed order replaces the old one. All SMS need a provider, the restaurant's texting switch on, and a number the customer gave on the call. An already-printed ticket is not reprinted when the pickup moves (staff can Reprint). Tests: `tests/pickup-change.test.ts`, `tests/cancel-text.test.ts`, e2e in `staff-and-orders.spec.ts`.


Phone line (LiveKit): inbound calls reach the worker through a LiveKit SIP dispatch rule. If the rule names an agent (explicit dispatch, as the project's existing `default` rule does with `food`), the worker must register with the same `AGENT_NAME` (read in the `WorkerOptions` at the bottom of `main.py`); an unnamed worker only gets automatic dispatch. Check with `lk sip inbound list` / `lk sip dispatch list` (needs `LIVEKIT_URL/API_KEY/API_SECRET` in the environment). The dialed number comes from the SIP participant attribute `sip.trunkPhoneNumber` and must be saved under Settings for a restaurant in E.164; unset `DEV_CALLED_NUMBER` when testing real calls so a wrong attribute name isn't masked. The `lk` CLI needs >=2.6.3 for `lk agent` commands.

Hanging up on goodbye (all calls, not only after an order): `end_call_after_goodbye()` also listens to `conversation_item_added`. If the CALLER says bye / goodbye (`caller_said_goodbye`) or the AGENT says a goodbye without asking a question (`is_goodbye`), it arms the hang-up (the line drops about 1 s after the agent finishes speaking, so its own goodbye is not cut off). Reason: models say goodbye but often do not call the `end_call` tool. `end_call` still exists and the prompt asks for it; the code does not depend on it. Evals `*-goodbye-*` check this (counted as hung up when `end_call` was called or the agent said goodbye). Earlier: after `submit_order` succeeds the agent arms `end_call_after_goodbye()` (`main.py`): once it has said the order number and goodbye (agent state returns to `listening`, then 1s of silence; or 20s of continuous speaking as a backup for realtime models, or 45s overall) `hang_up()` deletes the LiveKit room through the REST API with certifi's CA bundle (an agent that only leaves keeps the SIP caller connected). In console mode (fake job) it just ends the job. Agent logs state changes at INFO; set `AGENT_LOG_FILE` to also write them to a file.

Menu lookup: there is no SQL search or vector index. At call start the agent fetches the WHOLE available menu through `/api/agent/menu` and the model matches what the caller says to a dish itself; the server only validates ids exactly. For BIG menus (more than `MENU_SEARCH_THRESHOLD`, default 40, dishes — e.g. 150) the prompt holds only a names overview and the model must call the `search_menu` tool (`menu_search.py`, in memory over the fetched menu: exact/containment/bigram/edit similarity on dish names and ingredient words in descriptions; no extra dependencies). Ingredient/allergen/"do you have X" questions must go through search because the overview has no descriptions. Search results reuse the whole-menu option codes (`o1`…) so `add_item` stays valid. Optional choices are NOT asked before adding: `add_item` adds the dish at once (required choices only) and its result lists the optional choices not yet offered; the model asks once and `add_choice` (additive only) applies a yes — this guarantees a dish is never lost because the caller ignored an optional question. Agent tests: `cd apps/agent && uv run python -m pytest -q` (no network/LLM; runs in CI).

Agent behaviour: `build_instructions()` in `apps/agent/src/order_agent/main.py` is written for phone use (short plain-spoken replies, no markdown, prices in words, allergens never confirmed beyond the menu text, order read back once). The order lives only in the tools: `add_item`/`remove_item` mutate it (identical item+notes lines merge), `get_order` returns it, and the TOTAL is computed in code (`_summary`), never by the model. Prompt/tool changes should be checked with a scripted text-only conversation (`AgentSession.run(user_input=...)` against the local web API, no audio or LiveKit needed); these runs place real test orders in whichever restaurant `DEV_CALLED_NUMBER` points at, and the model's behaviour is not deterministic (it once confirmed items without calling `add_item`).

Call safety (LAUNCH_PLAN Phase 1): at call start the agent POSTs `/api/agent/calls` (`call_id` = room name, `caller` = SIP `sip.phoneNumber`); the server refuses blocked numbers (`blocked_numbers`, managed in `/admin`), more than 5 calls/hour per caller and more than 3 simultaneous calls per restaurant (`src/lib/call-limits.ts`, tracked in the `calls` table, ended via `/api/agent/calls/end`; stale after 15 min). Refused callers hear a polite sentence and the room is deleted; if the check itself is unreachable the call is allowed (logged). `call_guard.py` holds the pure logic: `CallClock` (8 min max with a 1-min warning, "are you still there?" after 20 s silence, hang-up at 30 s; override with `CALL_MAX_SECONDS`, `CALL_WARN_SECONDS`, `CALL_IDLE_PROMPT_SECONDS`, `CALL_IDLE_HANGUP_SECONDS`), `cart_key()` (idempotency key = call id + cart hash, stored in `orders.idempotency_key`, unique per tenant, so a retry returns the same order number) and `submit_with_retry()` (retry once on network/5xx; 4xx is "rejected" and the model fixes the order; otherwise logs `ALERT: order NOT saved`, the caller is told the restaurant will call back, and the call ends). Phone numbers are attached by the platform admin only (`/admin`); restaurants see theirs read-only in Settings. `orders.caller_number` stores the caller. Retention (D6): the `retention` compose service (``retention_sh` in docker-compose.yml`, daily at `RETENTION_HOUR` UTC) deletes `calls` rows and clears `orders.caller_number` older than `RETENTION_CALLER_DAYS` (default 90); orders themselves are kept. Routine agent logs show callers masked (`***4567`); the `ALERT: order NOT saved` line keeps the full number on purpose so staff can call back. Docker log rotation is by size (10 MB x 5), not time, so "14 days of logs" is approximate: check `docker compose logs` age on the server. Backups hold caller numbers for up to `BACKUP_KEEP` (14) days.

Opening hours: `tenant_settings.timezone` + `opening_hours` (restaurant-controlled, `/dashboard/settings`, logic in client-safe `src/lib/hours.ts`; null = always open). `/api/agent/menu` returns `{closed: true, hours}` outside them and the agent says the hours and hangs up. Web tests: `pnpm --filter web test` (node:test + tsx, needs a migrated `DATABASE_URL`; `tests/tenant-isolation.test.ts` calls every dashboard server action as restaurant A against B's ids with `requireTenant` mocked, and the agent order route; CI runs it with a Postgres service). Add new server actions to that test.

Phase 3 hardening: security headers + CSP come from `src/lib/security-headers.ts` via `next.config.ts` (CSP allows inline scripts/styles because Next needs them; HSTS also set in the `caddyfile` config in `docker-compose.yml`). Auth (`src/lib/auth.ts`): explicit rate limits (10 sign-ins/min per IP, 5 sign-ups/resets), client IP read from `AUTH_IP_HEADER` (default `x-forwarded-for`, `cf-connecting-ip` behind Cloudflare), 7-day sessions, Google never links into an unverified password account, signing up over an unverified pre-registration replaces it, and platform admins cannot use password sign-in (Google only; enforce 2-step verification on those Google accounts). Roles: `owner` manages menu/modifiers/settings/team (`requireOwner()` in `src/lib/roles.ts` guards those server actions; client-safe helpers in `role-utils.ts`); any other member is Staff (orders board + sold-out toggle). Evals (P4.2): `cd apps/agent && uv run python -m evals.run_evals [--runs N] [--only pickup-] [--threshold 0.9]` runs simulated phone calls over TEXT: an LLM "caller" follows a scenario goal (`evals/scenarios.py`, own test menu) against the real `OrderAgent`, with only `api.submit_order` stubbed (captured per call id because runs are concurrent). **Cost rule: automated text evals never use xAI.** The agent under test defaults to OpenAI or DeepSeek (whichever key is set; `EVAL_AGENT_PROVIDER` forces one) and the simulated caller is OpenAI/DeepSeek (`EVAL_CALLER_PROVIDER`); CI has no xAI key. The real Grok realtime model can still be evaluated by hand with an explicit `EVAL_AGENT_PROVIDER=grok` (text input only: covers prompt, tools and Grok's behaviour, NOT speech recognition or voice quality; the harness sets `SSL_CERT_FILE` to certifi's bundle for the xAI websocket). Pass = exactly the expected order was submitted (or nothing, for "not on the menu" calls); exit 1 if the overall pass rate is below the threshold. `EVAL_VERBOSE=1|all` prints failing|all transcripts. `evals/scoring.py` is unit-tested offline (`tests/test_evals.py`); live runs are in `.github/workflows/evals.yml` (agent changes on main, weekly, manual; needs `OPENAI_API_KEY` or `DEEPSEEK_API_KEY` as a repo secret). Baseline: DeepSeek pipeline 100% (Grok realtime was also 42/42 once, run by hand). Add a scenario whenever a real call goes wrong.

Browser tests (P4.3): `pnpm --filter web build && pnpm --filter web test:e2e` (Playwright, Chromium, `apps/web/e2e/`; needs a migrated `DATABASE_URL`; serves the production build on :3100 so it never clashes with `dev:web`). `e2e/seed.ts` (run through tsx because Playwright's loader cannot import the ESM auth library) creates a throwaway restaurant with an owner and a staff user (verified, password sign-in), a phone number and a dish, and removes them afterwards. Audit log: every mutation writes an append-only row to `audit_logs` via `audit()` in `src/lib/audit.ts` (who: user/admin/agent/system + email, which restaurant, action name, entity, one-line summary, before/after in `details`). It never throws (a failed write only logs to the console) and has no foreign keys so it outlives deleted restaurants/users/orders; nothing in the app updates or deletes rows. Action names live in `src/lib/audit-actions.ts` (order.created/updated/cancelled, menu_item.*, modifier_group.*, settings.*, team.*, call.*, auth.sign_in, admin.*, system.retention_purge); the platform admin browses/filters them at `/admin/audit` (restaurant, action group, who, text, dates, 50 per page; "Audit log" link on `/admin`). Rules: **any new server action or API route that changes data must call `audit()` and add its action to `AUDIT_ACTIONS`**; log only real changes (no entry for a no-op save), never secrets, and caller phone numbers only masked (`maskPhone`, because the audit log is not covered by the 90-day purge). Better Auth events (sign-in, invitations, member changes, restaurant created) are logged from hooks in `src/lib/auth.ts`; ``retention_sh` in docker-compose.yml` logs each purge that deleted something. Tests: `tests/audit.test.ts`, `e2e/zz-admin-audit.spec.ts` (mints a signed admin session cookie in `e2e/seed.ts` because admins cannot password-sign-in). Not logged: dashboard page views, failed/refused attempts by restaurant users, the email notifications themselves.

Cancel / change by phone: the agent tools `find_order(number)`, `cancel_found_order()`, `change_found_order()` call `/api/agent/orders/{lookup,cancel}`; a change rebuilds the cart from the old order (`order_items.modifiers[].optionId`, saved since this feature; older orders have `can_change: false`) and `submit_order` sends `replaces_order_number`, which cancels the old order and creates the new one in ONE transaction. Rules enforced on the server in `src/lib/order-changes.ts` (not by the model): only while the order is `new`, only from the same phone number that placed it (withheld number = refused), and "no such order" and "someone else's order" are indistinguishable (`no_match`) so numbers cannot be probed; the agent also stops after 3 misses. Restaurants are emailed on every cancel/change (`notifyOrderCancelled`, same recipients and opt-out as new-order emails) and it is audited (`order.cancelled`, refused attempts as `order.cancel_refused`). Tests: `tests/order-changes.test.ts`, `tests/test_order_changes.py`, evals `*-cancel-*` / `*-change-*`.

Human transfer: pressing 0 (SIP DTMF) or asking for a person (tool `transfer_to_human`) forwards the call to `tenant_settings.transfer_number`, which the restaurant owner sets in Settings (or the platform admin on `/admin`; also returned as `transfer_number` by `/api/agent/menu`; restaurant settings upserts never touch it). `transfer.py` holds the logic (announce, dial, report, keep the caller if it fails) and `build_transferer()` in `main.py` does the LiveKit SIP REFER transfer (`transfer_sip_participant`, needs a SIP trunk that supports transfers; untested on a real call). While forwarding, the time-limit/silence watchdog is paused; success and failure are audited (`call.transferred`, `call.transfer_failed`). No number set = the agent says nobody is available. **LiveKit-purchased phone numbers cannot do SIP transfers** (`ServerError unimplemented: we don't yet support transfers for this phone number type`); use your own SIP trunk (Twilio/Telnyx/...) with REFER/call transfer enabled for the restaurant's number. When a transfer fails the agent apologises, then reads the human line as a fixed script (`say_exact`, twice, digit by digit) so the caller can dial it directly.

Per-restaurant data (nothing is shared between restaurants): menu items and modifiers (`tenant_id`), notification emails (`tenant_settings.notify_emails`, owner-edited), address (`tenant_settings.address`, owner-edited in Settings → Restaurant details; given to the agent with the menu and spoken only if the caller asks), opening hours, and the human line (`transfer_number`, set by the restaurant OWNER in Settings → Restaurant details via `saveHumanLine`, and also editable by the platform admin on `/admin`; it may not equal any agent number, checked in `lib/human-line.ts`). The AGENT phone numbers (`phone_numbers`) are platform-admin only. A user can own several restaurants (restaurant switcher).

Dishes never mention modifier groups they do not have unless the caller asks (prompt rule, `tests/test_prompt_rules.py`).

xAI outages: in Grok mode the agent first checks xAI's key-info endpoint (`grok_available()`, free, cached 30 s; a check that itself fails never blocks calls). If the team is blocked/out of credit it logs `ALERT: xAI/Grok unavailable`, and either speaks a fixed "cannot take your order because of a system problem, call back later" message with Deepgram TTS only and hangs up (`GROK_FALLBACK=apology`, the default) or serves the call with the Deepgram + LLM pipeline (`GROK_FALLBACK=pipeline`). If the model connection dies mid-call (`close` event with an error) the same apology is spoken. Refusals and closed-hours messages now also use Deepgram TTS (not Grok), so they work while xAI is down. If the restaurant has a human line, the apology reads it twice, digit by digit (`spoken_number()`, `system_down_message()`). **The model never speaks a phone number**: the prompt forbids it, and when a tool tells the caller to phone the restaurant it queues the number as a fixed script with `session.say` (`OrderAgent._read_restaurant_number`, not awaited because a tool cannot wait for speech queued behind its own turn). xAI note: the realtime API returns 403 "used all available credits or reached its monthly spending limit" when the xAI team is out of credit, which makes every Grok-mode call fail at connect; check `curl -H "Authorization: Bearer $XAI_API_KEY" https://api.x.ai/v1/api-key` (`team_blocked`) before debugging anything else.

Kitchen printing (`PRINTING_PLAN.md`): a new/changed/cancelled phone order creates a `print_jobs` row per enabled `printers` row whose print agent is NOT revoked (a replaced Pi's printer would never collect it; revoking an agent also fails its waiting tickets with "the print agent was revoked"; the board's Printing / Waiting for the printer (offline) / Printed / Failed label comes from `printStateOf()` in `lib/print/state.ts`: "Printing…" only while a ticket is on its way to a printer whose agent is online (seen in the last 90 s); tickets stuck on a disabled printer, a revoked agent or an OFFLINE agent (an old Pi that was replaced but never revoked) never hide that the real printer printed, and with nothing printed yet and only offline printers the label is "Waiting for the printer (offline)"; `tests/print-state.test.ts`) (`lib/print/jobs.ts`, `enqueuePrint`, never throws; the server renders the ticket as a 1-bit PNG with `@napi-rs/canvas` + Noto Sans SC in `apps/web/assets/fonts`, `lib/print/render.ts`; dedupe key per order+kind+printer; CANCELLED only if the kitchen got the order; `tenant_settings.print_timing` immediate | on_accept (on_accept = print only after the restaurant confirms: when a printer exists the orders board's first button on a new order reads "Confirm & Print" instead of "Start preparing", it runs `setOrderStatus(id, "preparing")` which enqueues the ticket, once; `tests/confirm-print.test.ts`, `e2e/print.spec.ts`)). Service commands are a fixed allow-list (`lib/print/service.ts`, never a shell), queued by the owner (Settings -> Kitchen printing) or the platform admin (`/admin/printing`) and audited. Restaurant code cannot SELECT `print_agents.token_hash` (column grants). The agent self-updates from `/api/print/update` (`lib/print/release.ts`): the Go binaries are built into the WEB IMAGE by `apps/web/Dockerfile` (stage `agent`, from `apps/printer-agent`, version in `apps/printer-agent/VERSION`: bump it when the agent changes) and served by the web app at `/printer/` (a private GitHub repo cannot host downloads for a Pi); `PRINT_AGENT_VERSION` + `PRINT_AGENT_BASE_URL` (both) override to host elsewhere; local dev: `pnpm --filter web agent:build`; the CI job `printer-agent` (vet, test, cross-compile, VERSION format) must pass before the images build, installs with `apps/web/public/install-printer.sh`, and has a PIN-protected local setup page. Tests: `tests/print.test.ts`, `tests/print-api.test.ts`, `e2e/print.spec.ts`, `e2e/printagent.spec.ts` (needs `go`; runs the real binary), `cd apps/printer-agent && go test ./...`.
